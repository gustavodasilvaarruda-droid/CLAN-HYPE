Fluxo seguro: analisar JAR → guardar original em privado → proteger e testar o build → assinar a versão → publicar para o atualizador do Minecraft. Ofuscação automática ainda exige configurar o projeto Java/Fabric e um executor isolado; o upload sozinho não protege o código.

1. Enviar JAR para armazenamento privado

O upload registra o ID Fabric, versão, tamanho, SHA-256 e requisitos declarados no arquivo. Somente administradores podem enviar. Esta etapa não publica o JAR, nem prova que ele foi ofuscado, assinado ou testado no jogo.

Limpeza segura: use Apagar somente em arquivos pendentes ou rejeitados. Builds em teste e versões aprovadas/publicadas ficam bloqueados. Para descartar um build em teste, marque-o como Rejeitado na etapa 3 primeiro. O sistema não apaga arquivos automaticamente.

2. Registrar build candidato protegido

Esta etapa não seleciona o JAR original: ela recebe outro arquivo .jar, compilado/preparado fora do site, vinculado à versão que está em teste. A versão preparada passa por uma segunda verificação de integridade, classes de inicialização, dependências e atualizador. O site não faz proteção nem ofuscação sozinho. Não reenvie o original como se fosse um build protegido.

4. Publicar atualização assinada

A publicação só aceita o HYPE Client aprovado, acompanhado de manifesto Ed25519 assinado com a chave correspondente à versão instalada nos jogadores. O site valida a assinatura, versão, endereço, tamanho e SHA-256 do build candidato antes de registrar. O arquivo original nunca é publicado por engano.
